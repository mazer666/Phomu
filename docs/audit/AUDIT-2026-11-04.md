# Audit — Phomu, state `origin/main` (771338f)

**Date:** 2026-11-04
**Audited state:** `origin/main` = `771338f` ("feat: share compact game actions and
restore Timeline helpers"), eight commits above `beb12e3`
**Method:** a separate worktree on `origin/main`, all 12 gates, `cargo test --workspace`
(46 test binaries), clippy, `cargo fmt --check`, 298 vitest tests, the full
Playwright suite (72 tests, 21.7 min), probe scripts against the core, the GitHub
API for actions, PRs and releases.

**Summary:** The work of codex is substantial and, in most parts, careful. The
core is clean (clippy without a finding, fmt clean, 46 test binaries green), the
documentation kept pace (`REQUIREMENTS.md`, `CHANGELOG.md`, `docs/cr/CR-0003`,
acceptance protocols), and the new bridge surface got a gate of its own
(`platform/bridge-surface.json`). BUT: **the current `main` has never seen a green
CI run** — all eight commits were pushed with cancelled or red jobs, and both
deploys run without a dependency on the CI. The live state is therefore published
unverified. On top of that come ten red end-to-end tests, which I reproduced and
traced back to their causes.

---

## 1. The state of the pipeline (highest priority)

### 1.1 Not a single green CI run on the eight codex commits

| Commit    | CI run | Result                                      |
| --------- | ------ | ------------------------------------------- |
| `284d428` | 37     | **failure** — end-to-end, Android, Prettier |
| `43cb932` | 38     | cancelled — end-to-end, Android, Prettier   |
| `13aadde` | 39     | cancelled — end-to-end, Android, Prettier   |
| `613ea9f` | 40     | cancelled — end-to-end, Android, Prettier   |
| `5794083` | 41     | cancelled — end-to-end, Android, Prettier   |
| `81e5f07` | 42     | cancelled — end-to-end, Android, Prettier   |
| `771338f` | 43     | cancelled — end-to-end, Android, Prettier   |

The last green run is **my** `beb12e3` (run 36, 2026-10-31). The cause of the
cancellations is `cancel-in-progress: true` in `ci.yml:43` — every new push aborts
the running CI. With eight pushes inside ~24 hours and a suite that needs
21.7 minutes, the gate is systematically never finished.

**Why this is a finding and not a coincidence:** the abort logic is right for fast
iteration and wrong for a binding gate. The job is aborted exactly when a further
push arrives — that is, exactly when the code is most interesting. The proposal:
set `cancel-in-progress` to `false` and let the push server carry the
responsibility, or move the CI job into a workflow that follows the deploy with
`workflow_run`.

### 1.2 Both deploys run without the CI

`deploy.yml` and `deploy-cloudflare.yml` trigger on `push: main` and have **no**
`needs:` relation to the CI. Verified: the live state `771338f` (deploy at 16:18,
`success`) went out although its CI run was cancelled and two of its jobs were red.
Checked on the live site: `phomu.pages.dev` serves the wasm blob of the codex
version (587919 bytes), and the Mix-Tape is present in the delivered chunk.

This is the heaviest gap in the chain: **a state with a broken format job, a
broken Android job and unchecked end-to-end tests is in production.** Proposal:
couple both deploys to the CI via `workflow_run` and do not deploy when
`conclusion != success`.

### 1.3 The Android job fails at the SDK setup, not at the Kotlin

The job "Android shell" was red in **all seven** runs, and already before Gradle
was invoked:

```
Error: The process '/usr/local/lib/android/sdk/cmdline-tools/16.0/bin/sdkmanager'
failed with exit code 1
Warning: Failed to find package 'tools'
```

The job that I introduced myself in `beb12e3` installs `platform-tools`,
`platforms;android-35` and `build-tools;35.0.0` through
`android-actions/setup-android@v3` and then calls `sdkmanager` with package names
itself. The action now ships cmdline-tools 16.0, and `sdkmanager` no longer finds
the package `tools`.

**Consequence:** the Kotlin code of codex (the `GameScreen.kt` reduced from 369 to
139 lines, the new `TimelineTable.kt`, `PhomuCardBack.kt`) was **never compiled**.
My own Kotlin work from `beb12e3` neither. I checked the changes statically (the
new string keys `modes.timeline.tableHint`, `earlier`, `later`, `slotLabel`,
`beginning`, `end`, `swipeHint` exist in `en.json` and `de.json` and are carried
over by the generator into `res/`), but I cannot confirm that it compiles. The job
is `continue-on-error: true` — which is why nobody noticed.

**Proposal:** do not call `sdkmanager` by hand, but request the packages through
the `packages:` input of `android-actions/setup-android@v3`, or pin
`cmdline-tools;latest`. The job should block as soon as it runs.

### 1.4 The end-to-end job has 20 minutes, the suite needs 21.7

`ci.yml:112` sets `timeout-minutes: 20`. My complete run: **62 passed, 10 failed
in 21.7 min** (one worker, dev server). Even if all ten failures were fixed, the
gate would be **too slow for its own time limit** — it would always fail on the
timeout instead of on the content.

**Proposal:** raise the limit to 45 minutes and set `workers`. Playwright uses the
default here (one worker on a single core, otherwise 50 % of the cores); with four
workers the suite takes about six minutes. Both together make the gate usable in
the first place.

### 1.5 Prettier: 332 files, not formatted for a long time

`npm run format:check` reports **332 files** (at `beb12e3` it were 324). The job
is `continue-on-error: true`, and `local-ci.sh:56` runs it with the flag `"true"`
for information only. The job "Prettier format check" was red in all seven codex
runs.

**This is not a codex fault** but an old debt — it means, however, that formatting
is effectively switched off, and every new commit widens the gap. Proposal: either
run `prettier --write .` once as a commit of its own (formatting only, no
behaviour) and switch the job on, or drop the job and take formatting out of the
gate — a permanently red, ignored gate is worse than none.

## 2. The ten red end-to-end tests

I reproduced all ten and traced them back to their causes. **Seven are test
faults, not product faults** — but they block the suite and therefore the gate.

### 2.1 `feedback-mobile.spec.ts` ×2 — a race against the auto-dismiss (test fault)

`FEEDBACK_AUTO_DISMISS_MS = 5000` (`src/config/game-config.ts:54`). Measured:

```
Overlay visible after ms:    884
Opacity poll done after ms:  1107
Hit poll done after ms:      1688
boundingBox done after ms:   3036
Screenshot done after ms:    7740     ← the screenshot alone takes 4.7 s
Overlay still visible? false after ms: 7790
```

The test does `await expect(feedback).toBeVisible()`, checks the opacity, checks
the hit position, takes the box, takes a screenshot and then taps `feedback.tap()`.
Between the screenshot and the tap lie about 4.7 seconds in this environment — the
overlay is gone by then, and the tap waits 120 seconds for an element that never
comes back.

The third test of the same file (`feedback survives quick continuation`) is green
because it gets by without a screenshot. **This is not a product fault** but a
timing fault in the test: the screenshot belongs before the visibility check, or
the overlay needs a test option that switches the auto-dismiss off.

### 2.2 `library.spec.ts` ×3 — the test checks the production path (test fault)

`e2e/library.spec.ts:24` expects `src` = `/Phomu/covers/…`. The dev server runs
with `NEXT_PUBLIC_BASE_PATH=""` (`playwright.config.ts:44`) and therefore serves
`/covers/…`. Measured: `src attribute: /covers/7005f6d3fbf0.jpg`.

The test thus checks the **GitHub Pages path** (with the `/Phomu` prefix) while it
runs against the dev server without a prefix. Both deploys serve working covers:
`mazer666.github.io/Phomu/covers/…` → HTTP 200 and `phomu.pages.dev/covers/…` →
HTTP 200. There is also a `playwright.production.config.ts` that maps the prefix
correctly (`http://127.0.0.1:3102/Phomu`) — but `library.spec.ts` never runs under
that configuration.

**Proposal:** couple the expectation to `baseURL` instead of a hard-wired prefix,
or move the test into the production configuration.

### 2.3 `game-table.spec.ts:336` — the QR test (test fault)

Error: `strict mode violation: locator('[role="dialog"]') resolved to 2 elements`.
The Next.js dev overlay inserts a second dialog (`aria-labelledby="nextjs__container_errors_label"`).
`e2e/support/game.ts:45` hides the overlay with CSS (`nextjs-portal { display:none }`),
but **hiding is not enough** — the dialog stays in the DOM and disturbs
`page.locator('[role="dialog"]')`, which works over all matches with `evaluate`
(`support/reachability.ts:8`).

**Proposal:** change the helpers to `page.getByRole('dialog').filter(...)` or to an
application-specific selector instead of the global `[role="dialog"]`. That is
more robust and does not hit the dev overlay.

### 2.4 `game-table.spec.ts:304` — the dialog dialogue (test fault with a product part)

The test opens the scoreboard, clicks "Close" and checks `toBeHidden()` at once.
The dialog, however, closes through an exit animation (`framer-motion`,
`exit={{ x: '100%' }}`, spring 350/35). Measured:

```
5. Dialog visible after click: true
6. Dialog visible after 600ms:  false
```

`expect(dialog).toBeHidden()` checks immediately and loses the race against the
animation. **Product part:** during the exit animation the scoreboard panel
(`fixed right-0 top-0 h-full w-72 z-50`) still lies over the screen and swallows
clicks — in my probe run it blocked the next button press 172 times. The test does
not catch that, but a user could click into that window.

### 2.5 `mobile-clipping.spec.ts:174` @ 568×320 and `:193` — layout (product fault)

The lobby step in landscape format 568×320 and the settings during a game on
small screens do not keep the text inside the cards. This is the only group of
the ten failures with a real product reference — and it falls exactly into the
sphere the owner asked for first (no overflow, everything reachable).

### 2.6 `reveal-mobile.spec.ts` — the lyrics reveal (product fault)

`lyrics reveal keeps continuation reachable on Galaxy S23 viewports` — the
continue button of the Lyrics mode is not reachable on the Galaxy S23 viewport.
This is the same class of fault as 2.5 and touches the core promise of the mobile
journey.

**Assessment of the ten:** seven test faults, three product or edge findings. The
worst thing is not one of the tests but that the suite needs 21.7 minutes and
could therefore never turn green — the faults were never seen because the gate
was aborted beforehand.

## 3. Findings in the core (Rust)

The core is the healthiest sphere. `cargo clippy --workspace --all-targets`
without a finding, `cargo fmt --check` clean, 46 test binaries green. The new
bridge surface file (`platform/bridge-surface.json`) with the gate
`scripts/check-bridge-surface.mjs` is exemplary: every state-changing operation
names its bridge symbol, every deliberately unexposed one names the reason —
including the open gap `OPEN-BS-01` (no restoration of a session after a crash).
I did not expect that.

### 3.1 The Mix-Tape rotation works — I followed it over fourteen rounds

`GameMode::MixTape` selects the next member mode in `pick_mode()`
(`session/prompt.rs:27`) from `round_history`. Empirically with a mixed selection
(Mix-Tape + Timeline + Hint-Master), seed 7:

```
Round  1: vibe-check       flag=true
Round  2: timeline         flag=false
Round  4: hint-master      flag=false
Round  6: survivor         flag=true
Round  7: cover-confusion  flag=true
Round 13: vibe-check       flag=true
Round 14: survivor         flag=true
```

The rotation continues across the rounds in between, as described in `CR-0003`.
The cap on the points works as well: `points_possible` is never above 3 in the
Mix-Tape, while the standalone Timeline mode keeps its 4.

The order in `next_round()` (`session/rounds.rs:69-70`) is correct: `progress` is
reset **before** `pick_mode()` sets the flag — I suspected a fault there at first
and was wrong.

### 3.2 The pack-aware timeline (`prepare_timeline`) is clean

`core/phomu-core/src/session/timeline_setup.rs` (new, 39 lines) filters the years
by the selected packs, normalises legacy aliases, completes a small selection with
adjacent years and **fails** instead of falling back to unrelated years. Six tests
in `core/phomu-core/tests/timeline_packs.rs` cover it, including the core
"Pop does not receive classical centuries" and "an unknown pack fails". This is
exactly the right direction: the class of fault that stood open as A/B in my last
session is closed.

### 3.3 `timeline_slots` in the question view — a structural spoiler vector (high priority)

**This is the most important finding of the audit, and it comes from my own commit
`beb12e3`.**

`RoundContext` (`core/phomu-core/src/spoiler/view.rs:132`) carries
`timeline_slots: Vec<usize>`. The core fills them with
`valid_slots(song.year, &timeline_years)` (`session/prompt.rs:174`) — that is, with
the **slot indices in which the song would be correct**. That is the answer of the
Timeline mode, handed out in the **question** phase.

Verified empirically (song year 1985, years `[1970, 1980, 1990]`):

```
timeline_slots = [2]
Years = [1970, 1980, 1990]
Canonical slot for 1985 = 2 (between 1980 and 1990)
```

The web shell genuinely needs the field (`TimelineMode.tsx:88` → `validSlotSet`) to
judge the placement. So the solution of the mode sits in the payload of the
question phase — exactly what the rule **C-1** in
`docs/design/PLATFORM-ARCHITECTURE.md:1002` forbids:

> In the phase `question` the base hands the shell a `RoundView` that contains no
> field capable of revealing the solution.

The anti-spoiler test (`core/phomu-core/tests/anti_spoiler.rs`) only checks
whether title and year appear as **text** in the payload — the slot indices are
numbers and slip through. The gate does not see the breach.

**Why this counts:** the product lives on the promise that the solution is not in
the player's hands. A tool that reads the network traffic gets the answer of the
Timeline round before it is handed in — in every game, with no visible advantage.
On the web that is a tool in the hands of one; on the Android path it is the same
(`GameController.kt:352` maps the slots into the state of the shell).

**Proposal:** two ways, both feasible:

1. The shell does not judge the placement itself but asks the core whether the
   submitted answer was correct (the core has `valid_slots` anyway). Then
   `timeline_slots` disappears from the question view.
2. If the shell needs the slots for the preview, the core must be allowed to
   **mask** them — for example only the number of valid slots, not their indices.

The first way is cleaner and fits the existing architecture ("the base owns the
rule, the shell owns the picture"). It needs a change in `TimelineMode.tsx` and
one in `describeTimelineSlot`.

**Addition:** the Rust core did not have this field before — before `beb12e3` the
wasm bridge carried `timelineSlots: Vec::<usize>::new()` and only filled it in
the follow-up question through `context_of`, which itself only reached for the
song. The breach was therefore latent and moved into the core with my commit. I
did not notice it — and that is the point: **the anti-spoiler test checks the
form, not the effect.** A negative test that compares the question view against
the known valid slots would have found it.

### 3.4 Smaller core observations

- `GameMode::ALL` now has **seven** entries (`MixTape` was added), but the doc
  comment still says "EXAMPLE: `GameMode::ALL` has six entries"
  (`core/phomu-core/src/modes/mod.rs:68`). The constant `PLAYABLE` (six) is the
  right one and is used — the comment is simply stale.
- `session/state.rs:246` calls `pick_mode()` and then reads
  `self.state.round.progress.mix_tape_round` — it works, but it depends on the
  order. A comment at that place would defuse the trap for the next reader.
- The naming diverges: the core names the field `picked_fake: bool`
  (`modes/mod.rs:232`), the FFI names it `picked_line: Option<String>`
  (`answer.rs:51`). That is **right as it is** — the bridge carries the line, the
  core needs the flag so that the line does not travel to the device. The bridge
  resolves it against the invented line of the session. Only a comment in the core
  could explain why it does not know the line.

## 4. The Android shell

- **My Kotlin work lives on.** `GameController.kt` carries `timelineYears` and
  `timelineSlots`, `ModeAnswer.kt` uses `pickedLine` — codex took it over and
  developed it further. `GameScreen.kt` was reduced from 369 to 139 lines, the
  timeline moved into the new `TimelineTable.kt`.
- **The Android shell computes the number of slots itself**
  (`timelineYears.size * 2 + 1`, `TimelineTable.kt:38`) instead of using the slots
  of the core — although the core supplies them and `GameController.kt:352` maps
  them. That is the duplication the core architecture wanted to avoid. With three
  years both ways give four slots, so the arithmetic is right — but it lives in
  two places, and the Android variant reads `timelineYears.size * 2` in one place
  and `+ 1` in another.
- **`Icons.Filled.EmojiEvents`** in `GameScreen.kt:59` — a material icon, not an
  emoji in the text, but the last symbolic icon left in the shell, while the web
  shell has its own `Icon` set with graphics. The Android shell has no graphic
  layer of its own yet; that is an open gap, not a fault.
- **The screens carry no `testTags`:** my probe run found **zero** `data-testid`
  attributes on the game page. The web shell has them (`.phomu-primary-action`,
  `[data-slot="0"]`), the Android shell does not — so the Android shell cannot be
  checked automatically once the Android job runs.

## 5. Documentation, process, governance

### 5.1 The documentation kept pace — codex's strongest side

- `REQUIREMENTS.md` was **rewritten in substance**, not merely extended: GAME-017
  now describes the pack-aware starting years with the reference to
  `Session::prepare_timeline`, and the old reference to the deleted
  `randomInitialYears(3)` is gone. GAME-021/GAME-022 name the new verification
  (`cargo test -p phomu-core timeline_helpers_each_work_once_in_either_order`,
  `e2e/timeline-hint.spec.ts`).
- `docs/cr/CR-0003-card-table-and-mix-tape.md` records the **owner's decision**
  (Mix-Tape = three independent rounds, not three questions on one song; at most
  three points; no accounts, no synchronisation).
- Five acceptance protocols under `docs/acceptance/` (each with a date) that
  document the UI decisions against the measured state.
- `CHANGELOG.md` lists the changes under `[Unreleased]` following Keep a Changelog.
- The gates `check:doc-links` and `check:doc-language` are green.

**One deficiency:** the anti-spoiler breach from 3.3 is mentioned in **none** of
the acceptance protocols — the protocols document the visible decisions, not the
data level.

### 5.2 The bridge surface gate is the best piece in the diff

`platform/bridge-surface.json` lists every public operation of the session with
its bridge symbol; operations that are deliberately not exposed name the reason
and an open gap. The gate `scripts/check-bridge-surface.mjs` reads the file, the
public operations and the exports of all three bridges, and fails when one of
four rules is broken. This is exactly the kind of structural safeguard that
distinguishes this project — and it was missing before.

### 5.3 Two deploys, one documented address

`deploy.yml` (GitHub Pages, `mazer666.github.io/Phomu/`, **with** the `/Phomu`
prefix) and `deploy-cloudflare.yml` (`phomu.pages.dev`, **without** a prefix) both
run on every push to `main` — both are current at `771338f`, both answer HTTP 200,
both serve the covers. The README names only `phomu.pages.dev`.

That is not a fault, but it is an ambiguity with consequences: the
`library.spec.ts` test checks the path of the **GitHub Pages** deploy
(`/Phomu/covers/`), while the dev server runs without a prefix (see 2.2). Two
deploy targets with different paths and a test that hard-wires one of them — that
is the root of the failure.

**Proposal:** settle on a single deploy target and remove the other, or derive
the addresses in the test from `baseURL` instead of hard-wiring them. The two
secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are set.

### 5.4 What is missing in the process

- **No releases.** The GitHub API reports zero releases, zero open issues, ten
  closed PRs (all from before the reform). The release pipeline I set up
  (`.github/workflows/release.yml`, operator-triggered, `track=android`, signed
  APK as a prerelease) is in the repository but was **never triggered** — the four
  signing secrets are missing. The track order of the release plan therefore
  stays at stage 0.
- **The changelog knows no version.** Only `[Unreleased]`. Without a version no
  release artefact can be referenced.
- **The four new acceptance protocols** have no relation to a gate entry — there
  is no `docs/acceptance/` gate that checks whether a protocol belongs to a
  mandatory proof. With 14 protocols and 12 gates, the assignment exists only in
  the head of the author.

## 6. What I recommend, in this order

**Immediately (blocks the live operation):**

1. Couple the deploys to the CI (`workflow_run` + `conclusion == success`).
2. `cancel-in-progress: false` in the CI.
3. Raise the end-to-end time limit to 45 minutes, set `workers: 4`.
4. Fix the Android job's `sdkmanager` call, let the job block.

**Then (the core of the gate):** 5. Fix the ten end-to-end failures — seven test corrections (screenshot before the
visibility check, couple the prefix to `baseURL`, select `[role="dialog"]`
application-specifically, wait out the closing animation) and three product
findings (landscape lobby, lyrics reveal on the Galaxy S23, the dialog overlay
swallowing clicks). 6. Take `timeline_slots` out of the question view (3.3) and write a negative test
that checks the **answer**, not the text form. 7. Prettier: format once and switch the job on — or drop the job.

**Then (structure):** 8. Consolidate `src/styles/*.css` (1,231 lines, 18 of them `!important`) with the
Tailwind system, or document it as a deliberate second level — at the moment it
is unclear which level governs. 9. ~~Add `prefers-reduced-motion` to the three new style files.~~ **Not needed** — the rule in `game-layout.css:90` selects `*` with `!important` and therefore reaches the rules of the other files as well. The finding of the audit was too sweeping here. 10. Point the Android shell at the slots of the core; introduce `testTags` for the
Android screens. 11. Correct the `GameMode::ALL` comment.

**For the release sphere:** 12. Set the four signing secrets and trigger the release pipeline for
`0.2.0-beta.1`; update the entry in
`docs/releases/RELEASE-RECORD-ANDROID.md`.

`cargo clippy` (no finding), `cargo fmt --check` (clean), 298 vitest tests,
`tsc --noEmit` (no finding), ESLint (0 errors, 5 warnings), the Mix-Tape rotation

**Not checkable in this environment:** the compilability of the Kotlin code (no
Java/SDK/NDK), the behaviour on real devices (no Galaxy S23, no iPhone), the
performance budgets of `docs/BEST_IN_CLASS.md` (no reference hardware), the

**Not checked:** the 142 MB of covers in `public/covers/` (1649 files, all in the
repository — a matter for a separate look, not a finding), the visibility of the
four-eyes rule for the admin pages (unchanged by codex), the cost of the two
parallel deploys.
