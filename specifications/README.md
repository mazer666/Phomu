## Why it is like this

The old structure had three problems:

1. **No requirement IDs.** Behaviour was described in running text, not
   referenceable. Tests could not refer to a requirement.
2. **No separation of product and process.** Status, roadmap, test strategy and
   audit lay next to each other without saying which of them was binding.
3. **No place for decisions.** Architecture decisions existed only as
   paragraphs in running text.

The new set separates this: `REQUIREMENTS.md` says **what** holds;
`ARCHITECTURE.md` says **how**; `docs/adr/` says **why**; `ROADMAP.md` says
**how far**.

## What still applies here

The files in this folder are **not** historical states, but still active data:

- `specifications/quality-baseline.json` — the baseline against which
  `npm run validate-catalog` checks
- `specifications/duplicate-allowlist.json` — the allowed duplicates
- `specifications/catalog_issues_report.json` — the latest catalogue check
  report (regenerated by `npm run validate-catalog:report`)
- `specifications/assets/audio-assets-ap2.md` — the specifications for the audio
  files and their storage locations
